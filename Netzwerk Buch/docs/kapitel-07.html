      Auf dieser Seite

        Zwischen Chip und Server steht das Gateway: ein Gerät, das Notrufe hört und an den Server weiterreicht. Dieses Kapitel zeigt, welche Hardware für die Tests in Frage kommt, wie die Software aufgebaut ist und was bei der Aufstellung zählt.

        Kurz gesagt

        • Das Gateway reicht Pakete weiter, ohne sie lesen zu können.
        • Im Schultest ist es ein Heltec V3. Am Berg stehen die Gateways an einer Gondelstation.
        • Die Software trennt Funk und Netz und puffert bis zu 60 Pakete, wenn das WLAN ausfällt.

        Offen: Welches Gerät kommt an den Berg? Geplant ist ein LoRa-Gateway.

        Wie viele Gateways ein ganzes Skigebiet braucht und wo genau sie stehen sollen, klären erst Kapitel 8 bis 10. Hier geht es nur um das einzelne Gerät.

        Die Hardware im Test

        Im Schultest ist das Gateway ein kleines Funkboard, der Heltec V3. Beim Test am Berg stehen die Gateways an einer Gondelstation. Geplant ist dort ein LoRa-Gateway, Gerät und Anzahl stehen nicht fest. Ein Gateway auf Heltec-Basis braucht drei Teile, zusammen knapp 56€:

        TeilMengeWofür
        Heltec WiFi LoRa 32 V3, 868 MHz (ESP32-S3 + SX1262, kleiner Bildschirm)1hört die Chips, reicht die Pakete über WLAN an den Server weiter
        Stabantenne 868 MHz, 3 dBi (SMA), mit Adapterkabel IPEX auf SMA1mehr Reichweite als die beigelegte Antenne
        USB-C-Netzteil 5V, 2A, mit 2m-Kabel1Strom an der Station

        Fest. Es ist ausdrücklich die Version V3, nicht V4: Die Gateway-Software ist für den V3-Chipsatz gebaut.

        Wie die Software aufgebaut ist

        Der folgende Abschnitt beschreibt die Software laut Übergabe. Sie liegt nicht in diesem Repository. Wir haben die Test-Version gelesen, aber nicht ausgeführt, siehe Was geprüft ist. Laut Übergabe liegt die Gateway-Software im Paket skitag-test.zip im Ordner firmware/skitag_empfaenger, kompiliert mit ESP32-Core 3.0.7 für das Board „Heltec WiFi LoRa 32(V3)“, mit den Bibliotheken RadioLib, ArduinoJson und U8g2. Eingestellt wird sie über config.h: ein Name (E1, E2), bis zu drei WLANs (etwa ein Hütten-WLAN und ein Handy-Hotspot als Rückfall), die Server-Adresse, ein eigenes Gateway-Passwort und die Funkeinstellungen, die exakt zu denen des Chips passen müssen.

        Teil der SoftwareAufgabe
        Funk, auf Kern 1nimmt nur echte SkiTag-Pakete an (0xA7, 27 Byte), reicht sie über eine Warteschlange weiter, muss nie auf das Netz warten
        Netz, auf Kern 0schickt jedes Paket mit RSSI, SNR und Alter als POST /gw/up mit Bearer-Passwort an den Server; die Antwort enthält die Downlinks, die dann gesendet werden
        Pufferfällt das WLAN kurz aus, sammelt das Gateway bis zu 60 Pakete, statt sie zu verwerfen
        Lebenszeichenkommen keine neuen Pakete, meldet sich das Gateway trotzdem alle 10 Sekunden am Server
        Bildschirmzeigt WLAN-Status, Server ok oder Fehler, Paketzähler und den zuletzt gehörten Chip mit Signalstärke

        Die Verbindung zum Server ist verschlüsselt (TLS). Damit das Gateway sicher ist, mit dem echten Server zu sprechen, prüft es dessen Zertifikat von Let's Encrypt. Hängt das Gateway 60 Sekunden lang, startet eine eingebaute Überwachung es neu, der Watchdog.

        Entschieden, aber am PC geschrieben. Laut Übergabe ist diese Software fertig, lief aber noch nie auf echter Hardware. Erst der Schultest mit dem Heltec zeigt, ob sie auf dem Board so läuft wie geplant.

        Puffer und Vorrang

        Ist das WLAN weg, hält das Gateway laut Übergabe bis zu 60 Pakete zurück, je Paket 27 Byte plus RSSI, SNR und Alter. Bei vollem Puffer fallen in der Test-Version die neuesten Pakete weg. Wie schnell er voll ist, hängt davon ab, wie viele Pakete ein Gateway überhaupt dekodieren kann:

        LagePakete pro Sekunde60 Pakete voll nach
        5 Chips, alle 20 s0,25rund 4 Minuten
        Ein Kanal, bestmögliche Nutzung ohne Fensterrund 0,8rund 74 Sekunden
        Ein Kanal, lückenlos belegtrund 4,4rund 14 Sekunden
        8 Kanäle, je bestmöglich ohne Fensterrund 6,5rund 9 Sekunden
        500 Chips alle 20 s, jedes Paket empfangen25rund 2,4 Sekunden

        Gerechnet, nicht gemessen. Die 25 Pakete sind nur eine Obergrenze: Auf einem Kanal mit 226 ms pro Paket passen höchstens 4,4 Pakete pro Sekunde. Bei 500 Chips ist also schon der Kanal das Problem, siehe Kapitel 5. Für 5 Chips reichen 60 Pakete, für hunderte Chips nicht, egal wie viele Kanäle es gibt.

        Für den Betrieb schlagen wir deshalb einen Puffer in drei Klassen vor, den das Gateway ohne Schlüssel führen kann:

        KlasseInhaltSpeicherBei Platzmangel
        1, kritischPakete mit Notruf-Kennung im KopfEigener Bereich, je Chip nur das neueste, höchstens 32 PlätzeDas älteste Paket fällt weg. Ein echter Notruf kommt mit der nächsten Wiederholung wieder hinein.
        2, EreignisPakete mit Ereignis-Kennung, etwa GruppenrufEigener Bereich, höchstens 64 PlätzeÄltestes zuerst. Der Chip wiederholt ohnehin bis zur Empfangsbestätigung (ACK).
        3, PositionNormale PositionenJe Chip nur die neueste, erkannt an Chip-Nummer und ZählerÜberschreibt die ältere Position desselben Chips

        Gesendet wird in dieser Reihenfolge. Bei 500 Chips und rund 40 Byte je Eintrag braucht Klasse 3 rund 20 KB Speicher. Das ist nur eine Überschlagsrechnung, nicht auf dem Board geprüft.

        Damit das geht, braucht das Paket eine lesbare Kennung für die Klasse, denn das Ereignis selbst ist verschlüsselt. Diese Kennung wird vom Prüfwert mit abgedeckt, den nur der Server prüfen kann. Das Gateway hat keinen Schlüssel und soll auch keinen bekommen, weil es zugänglich steht. Es behandelt die Kennung also nur als Hinweis:

        • Ein gefälschtes Notruf-Paket löst keinen Alarm aus, denn der Server verwirft es am Prüfwert.
        • Eine Flut gefälschter Pakete kann höchstens Klasse 1 füllen. Die feste Platzzahl je Chip und Klasse begrenzt das, Klasse 2 und 3 bleiben unberührt.
        • Echte Notrufe überstehen das, weil der Chip bis zur Empfangsbestätigung wiederholt. Gegen Störsender hilft das nicht.
        • Die Kennung verrät Mithörenden, dass ein Notruf läuft. Inhalt und Position bleiben verschlüsselt.

        Bei Stromausfall ist der Puffer weg. Das verliert keinen bestätigten Notruf, denn das Gateway gibt nie eine Empfangsbestätigung. Ein Notruf im Puffer ist also unbestätigt, und der Chip wiederholt ihn. Dauerhaft gespeichert wird deshalb nur am Server, im Gateway nicht. Der Flash-Speicher würde das auch nicht lange aushalten.

        Aufstellung im Test

        Beim Test am Berg stehen die Gateways an einer Gondelstation. Welche das ist und wo genau dort, ist noch offen. Die Übergabe plant je ein Gateway innen an einem Fenster, möglichst hoch, mit senkrechter Antenne und Blick auf die Pisten. Strom und WLAN liefert die Station selbst, vorher muss geklärt sein, ob das dort genutzt werden darf.

        Geschätzt. Diese Aufstellung ist ein erster Plan, nicht gemessen: Wärmeschutzglas kann Funk stark dämpfen, eine Antenne außerhalb des Fensters wäre besser. Ob das an den Bergstationen so möglich ist, klärt Kapitel 10.

        Wenn mehrere Gateways gleichzeitig hören

        Hören mehrere Gateways denselben Chip, verwirft der Server das doppelte Paket über den Zähler, siehe Kapitel 4. Für Befehle an den Chip merkt sich der Server, welches Gateway ihn in den letzten 15 Minuten am besten empfangen hat, und schickt den Downlink über genau dieses.

        Das Ergebnis

        Entschieden: Im Schultest ist ein Heltec WiFi LoRa 32 V3 das Gateway. Beim Test am Berg stehen die Gateways an einer Gondelstation.

        Offen: Welches Gateway am Berg zum Einsatz kommt. Geplant ist ein LoRa-Gateway, die Anzahl steht nicht fest.

        Entschieden: Die Software trennt Funk und Netz auf zwei Kernen, damit der Funk nie auf das Netz warten muss, und puffert bis zu 60 Pakete bei einem WLAN-Ausfall. Fertig geschrieben ist sie, geprüft nur am PC.

        Offen: Ob sie auf echter Hardware wie geplant läuft, was bei einem Gateway-Ausfall geschehen soll, und wie sich das Gateway beim eigenen Server statt in der Cloud sicher anmeldet.
