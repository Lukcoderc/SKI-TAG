        Der Server

        Kapitel 12 · Stand 1. November 2026

        Der Server ist die Zentrale von SkiTag. Chips und Gateways liefern nur Daten, entschieden wird hier. Dieses Kapitel erklärt, was er tut, warum er bei KitzSki steht und trotzdem aus dem Internet erreichbar sein muss.

        Entschieden ist ein eigener Server vor Ort in der IT-Abteilung von KitzSki, kein gemieteter in der Cloud. Für den Schultest läuft derselbe Aufbau auf einem NAS, siehe Kapitel 18.

        Die Server-Software lag beim Schreiben nicht vor. Alles hier stammt aus der Übergabe und ist laut ihr nur am PC getestet, siehe Was geprüft ist.

        Was er tut

        AufgabeSo läuft es

        Wie er aufgebaut ist

        Der Server läuft auf Ubuntu 24.04 in Docker, geschrieben in Node.js 22 ohne npm-Pakete. Davor steht Caddy, das HTTPS übernimmt und das Zertifikat besorgt. Der Start ist ein einziger Befehl, und die Einstellungen stehen in config.json.

        Erst speichern, dann ACK

        Der Zustand liegt im Speicher und wird laut Übergabe alle 5 Sekunden nach daten/state.json geschrieben. Das Funk-Protokoll landet pro Tag in einer eigenen Datei. Für Positionen reicht das. Für Notrufe ist es gefährlich: Stürzt der Server ab, nachdem er ein ACK gesendet hat, aber bevor er gespeichert hat, ist der Notruf weg. Der Chip wiederholt ihn dann nicht mehr und warnt auch nicht.

        Ob der Server das heute so macht, wissen wir nicht, denn der Code lag nicht vor. Gefordert ist diese Reihenfolge:

        1. Paket prüfen und entschlüsseln.
        2. Notruf in ein Protokoll schreiben, das nur wächst, und mit fsync wirklich auf den Datenträger bringen.
        3. Erst dann das ACK in die Antwort an das Gateway legen.
        4. Beim Start zuerst dieses Protokoll einlesen und alle offenen Notrufe weiterführen, samt Zählern. Die Uhr T0 läuft dabei weiter, sie beginnt nicht neu.

        Das muss schnell gehen, denn das Gateway sendet eine Antwort nur bis 1,4 Sekunden nach dem Empfang. Ein NAS oder Server mit Schreibcache braucht einen Datenträger, der fsync wirklich einhält, sonst ist die Zusage wertlos.

        Als zweite Sicherung schlagen wir vor: Der Chip meldet in jedem Paket das Status-Bit „Notruf läuft“. Sieht der Server dieses Bit und kennt keinen offenen Notruf, legt er ihn neu an und meldet das. Ob der Chip das Bit nach dem ACK weiter setzt, muss Maximilian bestätigen.

        Warum vor Ort und trotzdem im Internet

        Vor Ort heißt: eigene Kontrolle und keine laufende Miete. Es heißt nicht: unabhängig vom Internet. Die App läuft über Mobilfunk, sie erreicht den Server also von außen. Drei Gegenstellen brauchen ihn:

        WerVon woWozu
        GatewaysAus dem Netz der Bergbahn oder über WLANPakete abliefern, Antworten holen
        Apps von Gästen und MitarbeiternÜber Mobilfunk aus dem InternetPositionen sehen, Notrufe annehmen
        Let's EncryptAus dem Internet oder über DNSPrüfen, dass die Domain uns gehört

        Wie er erreichbar wird

        Die Domain braucht ein gültiges Zertifikat, denn das Gateway prüft es. DuckDNS war für einen Cloud-Server gedacht. Für den Betrieb empfehlen wir eine eigene Domain und diesen Aufbau:

        1. KitzSki gibt Port 443 für den Server frei, am besten in einem abgetrennten Netzbereich.
        2. Caddy holt das Zertifikat über Port 80 oder über einen DNS-Eintrag.
        3. Im Netz der Bergbahn zeigt die Domain direkt auf die interne Adresse. Gateways erreichen den Server dann auch, wenn das Internet ausfällt.

        Ob die IT das so erlaubt, ist nicht geklärt. Das ist nur ein Vorschlag.

        Das Docker-Setup lag uns nicht vor. Vor dem Betrieb ist darin zu prüfen: Startet der Dienst nach einem Absturz oder Stromausfall von selbst neu? Liegen daten/ und die Zertifikate außerhalb der Container, damit ein Update sie nicht löscht? Prüft ein Gesundheitstest, ob der Server wirklich arbeitet und nicht nur läuft?

        Wie groß er sein muss

        Die Datenmenge aus dem Funk ist klein. Die Rechnung für das Funk-Protokoll nimmt rund 200 Byte pro Zeile und 8 Stunden Betrieb an, beides geschätzt:

        ChipsPakete pro SekundeProtokoll pro Tag
        5, Test0,25rund 1,4 MB
        50025rund 144 MB

        Die 25 Pakete sind eine Obergrenze, die ein Kanal gar nicht erreicht, siehe Kapitel 8. Nicht der Funk begrenzt den Server, sondern die offenen Live-Verbindungen der Apps. Jede App hält mindestens einen Stream offen. Ohne HTTP/2 erlaubt ein Browser nur 6 solcher Verbindungen. Wie viele Apps der Server gleichzeitig trägt, muss ein Lasttest zeigen.

        Wer sich kümmert

        Das Ergebnis

        Entschieden: Eigener Server vor Ort bei KitzSki, mit Docker und Caddy. Das Paket bleibt gleich, nur der Standort ändert sich.

        Geschätzt: Die Funkdaten sind klein: Bei 500 Chips sind es rund 25 Pakete pro Sekunde und rund 144 MB Protokoll am Tag.

        Offen: Ob ein ACK erst nach dem dauerhaften Speichern kommt, dazu Freigabe durch die IT, eigene Domain, Betreuung und Backup.
